# Load tests (k6)

Two scripts check the v1 non-functional targets in the design spec, section 11. They are run by hand
against a running stack. CI does not run them.

| Script | What it measures | Target (spec section 11) |
|---|---|---|
| `k6/api.js` | 50 VUs reading four non-VCS endpoints: project, run list, run detail, project config | API p95 < 300 ms |
| `k6/runs.js` | 8 VUs, each starting one dry run of the 200-operation spec with all outputs, and polling it to a terminal status | Run p95 < 3 min |

The thresholds are the v1 section 11 targets, stated plainly:

- `api.js`: `http_req_duration{group:::non-vcs}` p(95) < 300 ms, `http_req_failed` rate < 1%, and
  `checks` rate > 99%. The checks threshold makes a missing endpoint, such as a 404 on run detail,
  fail the run instead of passing on the other three.
- `runs.js`: `run_duration` p(95) < 180000 ms, `run_failures` rate = 0, and `http_req_failed` rate < 1%.
  `run_duration` covers successful runs only, so a fast failure cannot pull the p95 down. A run that
  ends `FAILED` or `CANCELLED`, that stops at `AWAITING_APPROVAL`, or that has not finished after
  10 minutes counts as a failure. `AWAITING_APPROVAL` and timed-out runs are cancelled best effort.

## Prerequisites

- A running stack reachable from the machine that runs k6, for example the prod compose from
  `deploy/compose/docker-compose.prod.yml`.
- The worker must run with the pipeline enabled, as Spring property `emitkit.worker.pipeline.enabled=true`
  (environment form `EMITKIT_WORKER_PIPELINE_ENABLED=true`). Nothing in `deploy/` sets it yet, so set it
  for the worker container before the run.
- Docker, to run k6 from the `grafana/k6:2.4.0` image. No local k6 install is needed.
- Capacity: the target assumes the prod compose's 2 worker replicas (`replicas: 2` in
  `deploy/compose/docker-compose.prod.yml`) with 4 sandbox slots each (`emitkit.sandbox.max-concurrent`
  defaults to 4), so 8 runs can run at once. A single-worker dev stack queues 4 of the 8 runs, and their
  `run_duration` then includes queue wait.

## Seed data

- A project whose repo holds the 200-operation fixture at the spec path the project is configured with.
  The fixture is `backend/generators/core/src/testFixtures/resources/golden-inputs/big-200-ops.yaml`,
  generated by `python3 scripts/gen-big-spec.py`.
- Project config for `runs.js`, so each run covers the section 11 workload (200 operations, all outputs):
  - `outputs`: `SDK`, `CLI`, `MCP`, `DOCS`
  - `sdkLanguages`: `typescript`, `python`, `java`. The config also needs the fields each language
    uses: `npmScope` is optional for typescript, `pypiName` is required for python, and `mavenGroupId`
    and `mavenArtifactId` are required for java.
  - `breakingGate`: `ALLOW`. With `REQUIRE_APPROVAL`, a breaking change parks the run at
    `AWAITING_APPROVAL`, and with `BLOCK` it fails the run. Both count as failures here.
  - AI: off. No AI key is saved, so the docs output uses templates and makes no external calls. With AI
    on, the docs output calls the AI provider during the run, and that latency is then part of the
    measured time. Note which setting you used with the result.
  - Set these in the project's config page in the UI, or with `PUT /api/v1/projects/{id}/config`.
- `api.js` needs at least one run on that project (it reads the first run in the list). Start one
  dry run in the UI first. `api.js` fails in setup, before any load, when the project has no run.

## Credentials

The API has no token login. The scripts send the GitHub login session cookie:

1. Sign in to the stack in a browser.
2. Open the browser developer tools, find the cookie named `SESSION` for the site, and copy its value.

The scripts take the CSRF token from the `XSRF-TOKEN` cookie that the API sets on each response, so no
CSRF value needs to be supplied. The session cookie is a credential: do not commit it, and keep it out
of the command line and shell history, as the commands below do.

## Running

Export the non-secret values, then read the session cookie without echoing it. Docker then takes
`SESSION` from the environment by name, so its value never appears in the command line:

```bash
export BASE_URL=https://emitkit.example.com   # no trailing slash needed
export PROJECT_ID='<project id>'
read -rs SESSION && export SESSION            # paste the SESSION cookie value, then Enter

docker run --rm -e BASE_URL -e SESSION -e PROJECT_ID -v "$PWD/perf/k6:/scripts:ro" \
  grafana/k6:2.4.0 run /scripts/api.js

docker run --rm -e BASE_URL -e SESSION -e PROJECT_ID -v "$PWD/perf/k6:/scripts:ro" \
  grafana/k6:2.4.0 run /scripts/runs.js
```

Add `--network host` to the `docker run` when `BASE_URL` points at `localhost`, so the container can
reach the host.

Each script exits non-zero when a threshold fails. A missing `BASE_URL`, `SESSION` or `PROJECT_ID`
stops the script before any request, with a message that names the variable. `runs.js` also makes one
preflight request before the load starts. A bad `SESSION` stops it there with `HTTP 401 (check SESSION)`,
and no runs are started.

## Reading the result

- `api.js`: check the `{ group:::non-vcs }` line of `http_req_duration` against `p(95)<300`, and the
  `checks` line against `rate>0.99`.
- `runs.js`: check `run_duration` against `p(95)<180000` (ms), and `run_failures` against `rate==0`.
  With 8 runs per execution, the p95 is close to the slowest run. Repeat the run for a more stable figure.
